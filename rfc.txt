1.  Introduction

   Zappy is a network simulation game built around a single server
   (zappy_server) that hosts a world inhabited by several teams of
   players competing against each other. The world is a flat,
   wrap-around tile map (exiting one edge brings a player back on the
   opposite edge) on which mineral and food resources are scattered
   and periodically respawned.

   The goal of each team is to reach the maximum elevation level with
   at least six of its players. To rise in level, players must
   perform an "incantation" ritual on a shared tile, gathering a
   required number of players of the same level along with specific
   quantities of stones. The first team to get six players to the
   maximum level wins the game.

   Players are driven by autonomous AI clients connected to the
   server over the network; once launched, a client receives no
   further input from the user and acts solely through the protocol
   described in this document. A graphical client (GUI) can also
   connect to the server, using a dedicated extension of the
   protocol, to observe and render the state of the world in real
   time without influencing gameplay.

   Three binaries compose the project:
     - zappy_server: generates and runs the world (C++).
     - zappy_gui:    a graphical, read-only observer (OpenGL).
     - zappy_ai:     an autonomous client driving a player (python).


2.  Terminology

   Trantor
        The name of the planet/world simulated by the server. It is
        geographically flat (no relief) and topologically wraps
        around itself: a player leaving the map on one side
        reappears on the opposite side.

   Trantorian
        An inhabitant of Trantor, i.e. a player. Trantorians are
        bodiless, blurry, and occupy the entire tile they stand on.
        They are pacifists, can overlap freely with other
        Trantorians on the same tile, and cannot distinguish the
        facing direction of another Trantorian they encounter. Their
        vision range is limited and grows with their elevation level.

   Egg
        The result of a successful `Fork` command. An egg occupies a
        team slot; when a new client connects to that team, a
        pending egg is selected at random and hatches into a new
        player with a random orientation.

   Elevation / Incantation
        The ritual by which a group of players of the same level,
        gathered on one tile with the required stones, all advance to
        the next level simultaneously.

   Time unit
        Trantor's unit of time. The duration of an action is given by
        action_time / f, where f is the server's frequency parameter
        (reciprocal of the time unit), set with the `-f` server
        argument.


3.  Protocol

3.1.  Transport

   All communication between the server and its clients (AI clients
   and GUI clients) is carried over TCP sockets. The server listens
   on a single port, given at startup, and multiplexes all client
   sockets using `poll`.

   Every command and every response is transmitted as a character
   string terminated by a newline ('\n'). Arguments noted between
   angle brackets (e.g. <object>) are placeholders to be replaced by
   an actual value. If the server receives a command it does not
   recognize, or a recognized command with invalid parameters, it
   must respond "ko".

   A client may send up to 10 requests in a row without waiting for a
   response; requests beyond that limit are not taken into account by
   the server until prior ones are processed. Requests are buffered
   and executed in the order they were received; the execution delay
   of a command only blocks the player that issued it.

3.2.  Connection Handshake (AI client)

   1. The client opens a TCP socket on the server's port.
   2. The server and the client exchange the following messages:

        <--  WELCOME\n
        -->  TEAM-NAME\n
        <--  CLIENT-NUM\n
        <--  X Y\n

      Where:
        - TEAM-NAME  is the name of the team the client wants to join.
        - CLIENT-NUM is the number of remaining available slots for
          that team. If this number is >= 1, the client occupies a
          slot and becomes a player.
        - X Y        are the width and height of the world.

   The reserved team name `GRAPHIC` is used by the GUI client to
   authenticate itself as an observer instead of a regular player
   (see Section 5.2).


4.  Architecture

   The server is executed as a single process and a single thread; no
   active waiting is performed at any point.

   - Core / ArgParser:
       At startup, the Core parses all command-line arguments through
       the ArgParser class, which is responsible for registering all
       supported flags (-p, -x, -y, -n, -c, -f) and for handling
       process signals.

   - Network / Socket:
       The Socket class manages client connections at the transport
       level (accepting new connections, reading/writing raw data).

   - Network / ClientHandler:
       The ClientHandler is responsible for retrieving, via `poll`,
       the data available on a given client socket, and storing it
       in a per-client command queue.

   - Network / CommandParser:
       The CommandParser processes the input retrieved by the
       ClientHandler from the command queue and executes the
       corresponding function in the server.

   - Commands:
       Each command sent by an AI client (Broadcast, Look, Take,
       Set, Forward, etc.) is handled by a dedicated Commands
       implementation.

   - GUI notifications:
       Independently of AI command processing, the server sends
       commands to every connected GUI client to keep it informed
       of events occurring in the world (player movement, death,
       incantation, egg laying, etc. -- see Section 5.2).

   - Simulation:
       The Simulation is responsible for the behaviour of players and
       of the world: movement, resource spawning, inventories,
       incantations, eggs, and elevation rules.

4.1.  Life handling

   Every team starts the game with a fixed number of available slots,
   each represented in the world by an egg. When an AI client connects
   to a team that still has at least one egg, one pending egg of that
   team is selected and replaced by a new player: the egg is removed
   from the world and the player is added in its place, with a
   random orientation.

   Once spawned, a player holds a life counter expressed in time
   units. A newly hatched player starts with 10 life units, i.e.
   1260 time units (10 * 126), or 1260/f seconds. This counter
   decreases continuously as time passes.

   To stay alive, the player must consume food it has previously
   collected in its inventory: each unit of food consumed restores
   126 time units of life. A player that lets its life counter reach
   0 without having eaten dies immediately.

   On death:
     - the player is removed from the world (its inventory and
       position are discarded);
     - the team slot it occupied is freed;
     - the team slot counter is decremented;
     - the server notifies every connected GUI client (`pdi #n`, see
       Section 5.2) so they can update their representation of the
       world state;
     - the corresponding AI client receives the `dead` response (see
       Section 5.1) and is disconnected.

5.  Commands

5.1.  Client/AI Commands

   Each player only responds to the following commands:

   +------------+----------+------------+------------------------------+
   | Action     | Command  | Time limit | Response                    |
   +------------+----------+------------+------------------------------+
   | move fwd   | Forward  | 7/f        | ok / ko                     |
   | turn right | Right    | 7/f        | ok / ko                     |
   | turn left  | Left     | 7/f        | ok / ko                     |
   | look       | Look     | 7/f        | [tile1, tile2, ...]         |
   | inventory  | Inventory| 1/f        | [linemate n, sibur n, ...]  |
   | broadcast  | Broadcast| 7/f        | ok / ko                     |
   |            | <text>   |            |                              |
   | team slots | Connect_nbr | -       | value                        |
   | fork       | Fork     | 42/f       | ok                           |
   | eject      | Eject    | 7/f        | ok / ko                      |
   | take obj.  | Take <object> | 7/f   | ok / ko                     |
   | set obj.   | Set <object>  | 7/f   | ok / ko                     |
   | incantation| Incantation   | 300/f | Elevation underway /        |
   |            |               |       | Current level: k / ko       |
   | death      | -             | -     | dead                         |
   +------------+----------+------------+------------------------------+

   All commands are sent as a string ending with a newline. In case of
   a bad or unknown command, the server answers "ko".

   The `Look` command returns the content of every tile within the
   player's field of vision, ordered from the player's own tile
   outward, line by line, left to right. The response format is:

        [tile0, tile1, tile2, ...]

   Each tile lists the objects present on it (players and/or
   resources), separated by spaces, e.g.:

        [deraumere:2, thystame:1 player:3]

   Tiles are separated by a comma, optionally followed by a space.
   An empty tile is represented by an empty field between separators.

   Below is a short description of each command, with the input sent
   by the client and the output returned by the server, in both the
   success and the failure case.

   Forward
        Input:   "Forward\n"
        Success: the player moves one tile forward in the direction
                 it is currently facing (with wrap-around on map
                 edges); the server replies "ok\n".
        Failure: none (the command always succeeds for a living
                 player); an unknown/malformed command still replies
                 "ko\n".

   Right / Left
        Input:   "Right\n" / "Left\n"
        Success: the player turns 90 degrees clockwise / counter-
                 clockwise on the spot; the server replies "ok\n".
        Failure: none; replies "ko\n" only for a malformed command.

   Look
        Input:   "Look\n"
        Success: the server replies with the content of every tile in
                 the player's field of vision (Section 6 of the
                 subject), e.g. "[player, , thystame, , food, ...]\n".
        Failure: replies "ko\n" if the command itself is malformed.

   Inventory
        Input:   "Inventory\n"
        Success: the server replies with the quantity held of each
                 resource and the player's remaining life, e.g.
                 "[food 345, sibur 3, phiras 5, ..., deraumere 0]\n".
        Failure: replies "ko\n" if the command itself is malformed.

   Broadcast <text>
        Input:   "Broadcast <text>\n"
        Success: every connected player receives
                 "message K, <text>\n", where K is the tile number
                 indicating the direction the sound came from
                 (Section 7 of the subject); the broadcaster itself
                 receives "ok\n".
        Failure: "ko\n" if no text is given.

   Connect_nbr
        Input:   "Connect_nbr\n"
        Success: the server replies with the number of slots still
                 available (eggs not yet hatched) for the sender's
                 team, e.g. "3\n".
        Failure: none; replies "ko\n" only for a malformed command.

   Fork
        Input:   "Fork\n"
        Success: the player lays one egg on its own tile, adding a
                 new connection slot to its team; the server replies
                 "ok\n".
        Failure: none; replies "ko\n" only for a malformed command.

   Eject
        Input:   "Eject\n"
        Success: every other player sharing the tile is pushed one
                 tile away in the direction the ejecting player is
                 facing (destroying any egg laid on that tile), and
                 each of them receives "eject: K\n" (K being the
                 direction the push is coming from); the ejecting
                 player receives "ok\n".
        Failure: "ko\n" if the player is alone on its tile.

   Take <object>
        Input:   "Take <object>\n"
        Success: one unit of <object> is removed from the tile and
                 added to the player's inventory; the server replies
                 "ok\n".
        Failure: "ko\n" if the tile holds no unit of <object>, or if
                 <object> is not a valid resource name.

   Set <object>
        Input:   "Set <object>\n"
        Success: one unit of <object> is removed from the player's
                 inventory and dropped on its tile; the server
                 replies "ok\n".
        Failure: "ko\n" if the player does not hold <object>, or if
                 <object> is not a valid resource name.

   Incantation
        Input:   "Incantation\n"
        Success: if the tile holds the required number of players of
                 the same level and the required stones (Section 5 of
                 the subject), the incantation starts and every
                 participant receives "Elevation underway\n"; once it
                 completes, the stones are consumed and every
                 participant is raised one level and receives
                 "Current level: k\n" (k being the new level).
        Failure: "ko\n" immediately if the prerequisites are not met
                 when the ritual starts, or to every participant if
                 they are no longer met when it ends.

   Death
        Input:   none -- triggered automatically when the player's
                 life counter reaches 0 (Section 4.1).
        Success: the server sends "dead\n" to the corresponding
                 client and closes its connection; the player is
                 removed from the world and the team slot is freed.
        Failure: not applicable.

5.2.  GUI Protocol

   A GUI client authenticates by sending `GRAPHIC` as its team name
   during the handshake (Section 3.2). Once recognized, the server
   exchanges the following messages with it:

7.  Server Logging

7.1.  Log Format

   Every notable server event is recorded by the `Logger` class
   (src/server/Logger/Logger.hpp) through the `Logger::log` method.
   Each entry follows a fixed structure:

        code - message (key=value, key=value, ...)

   The parenthesised key=value group is omitted when no fields are
   attached to the event.  Examples:

        030 - Client : connection established
        015 - Right : player turned right (rotation=90)
        8422 - Incantation : failed, conditions not met at start

   Codes are 3 or 4 decimal digits.  The first digit (or first two
   digits for 84xx) identifies the semantic category of the event;
   the remaining digits identify the specific event within that
   category.

7.2.  Code Ranges

   Three categories are currently defined:

   0xx -- Success
        The operation completed normally.  The sub-ranges are:

        00x   Poll / event-loop lifecycle.
              Example: 000 -- Poll initialised successfully.

        01x   Command execution (one code per AI command).
              All fourteen player commands each have a dedicated
              success code; see Section 7.3 for the hex-extension
              rule that allows more than ten codes in this block.

        02x   World events (resource spawning).
              Example: 020 -- resource spawned on a tile.
                       021 -- automatic periodic resource spawn.

        03x   Client connection lifecycle.
              Example: 030 -- connection established.
                       032 -- client disconnected cleanly.

        04x   Player lifecycle and state.
              Example: 040 -- player created.
                       041 -- player levelled up.
                       042 -- player frozen (incantation started).
                       043 -- player unfrozen (incantation ended).
                       044 -- player died.

        05x   Parsing.
              Example: 050 -- command recognised and dispatched.

   1xx -- Information
        Informational events that do not indicate success or failure.

        11x   Parsing / input.
              Example: 110 -- raw input received by CommandParser.

        12x   Client connection events (attempt / disconnection).
              Example: 120 -- new connection attempt detected.
                       121 -- disconnection detected.

   84xx -- Failure
        An operation could not be completed.  The sub-ranges are:

        840x  Poll / event-loop errors.
              Example: 8400 -- poll failed, unknown error.
                       8401 -- poll failed, out of memory (ENOMEM).

        841x  Parsing errors.
              Example: 8410 -- unknown command received.

        842x  Command execution failures (one code per AI command).
              Example: 8422 -- Incantation failed, conditions not
                               met at start.
                       8426 -- Take failed, item not on tile.

        843x  Client connection failures.
              Example: 8432 -- client disconnected unexpectedly.

        844x  Player action rejections and egg destruction.
              Example: 8441 -- action rejected, player is frozen.
                       8442 -- action rejected, player is dead.
                       8443 -- egg destroyed by ejection.

        845x  World update failures.
              Example: 8451 -- tile update failed.

7.3.  Hex Extension for Dense Blocks

   Each log code is at most four characters long, as required by the
   BNF grammar ("3DIGIT / 4DIGIT").  The 01x command block covers
   fourteen AI commands, which exceeds the ten slots available with a
   single decimal digit (0-9).

   Once the decimal digits 010-019 are exhausted, the block continues
   counting in hexadecimal for the last character: 01A, 01B, 01C.
   The same convention applies to any other block that needs more than
   ten codes.  The full 01x command mapping is:

        010  Fork
        011  Broadcast
        012  Incantation : started
        013  Incantation : completed
        014  Forward
        015  Right
        016  Left
        017  Look
        018  Inventory
        019  Eject
        01A  Take
        01B  Set
        01C  Connect_nbr

7.4.  Implementation and Examples

   Logs are emitted by calling `Logger::log` at the relevant call
   site.  The call sites are co-located with the operation they
   describe; there is no centralised logging middleware.

   Representative call sites and their codes:

        ClientHandler::handleClients  (before the poll loop)
             000 - Poll : initialized successfully

        ClientHandler::addClient
             120 - Client : new connection attempt
             030 - Client : connection established

        ClientHandler::removeClient
             032 - Client : disconnected cleanly
             8432 - Client : disconnected unexpectedly

        CommandParser::feed
             110 - Parsing : input received

        CommandParser::_dispatch
             050 - Parsing : command valid
             8410 - Parsing : unknown command

        CommandParser::executeNext
             8441 - Player : action rejected, player is frozen
             8442 - Player : action rejected, player is dead

        Commands::Forward
             014 - Forward : player moved
             8424 - Forward : failed

        Commands::Right / Commands::Left
             015 - Right : player turned right (rotation=<degrees>)
             016 - Left  : player turned left  (rotation=<degrees>)

        Commands::Look
             017 - Look : response sent (response=<tile-list>)

        Commands::getInventory
             018 - Inventory : response sent (<item>=<count>, ...)

        Commands::Broadcast
             011 - Broadcast : message sent
             8421 - Broadcast : failed

        Commands::Fork
             010 - Fork : new egg laid
             8420 - Fork : failed

        Commands::Eject
             019 - Eject : players ejected
             8425 - Eject : failed, no players to eject
             8443 - Player : egg destroyed by ejection

        Commands::Take
             01A - Take : item taken
             8426 - Take : failed, item not on tile

        Commands::Set
             01B - Set : item dropped
             8427 - Set : failed

        Commands::Connect_nbr
             01C - Connect_nbr : response sent

        Commands::beginIncantation
